## 二、为什么需要服务注册框架？

### 2.1 现状问题

当前 WaLiAPI 的所有 HTTP 路由都直接写在 `router.rs` 的 `create_router` 函数里。随着功能增多：

- 知识库有 15+ 个 CRUD + 搜索路由
- MCP Server 有 3 个 SSE/JSON-RPC 路由
- 未来可能还有更多服务（Webhook、OAuth 等）

如果继续堆在 router.rs，文件膨胀到难以维护，而且每个服务的路由、状态检查、生命周期管理都散落在各处。

### 2.2 Service trait 的设计思路

借鉴微服务架构中的 **Service Registry** 模式，但适配本地单进程场景：

```
┌─────────────────────────────────────────────────────┐
│              ServiceRegistry                         │
│  ┌───────────────┐  ┌───────────────┐               │
│  │ Knowledge      │  │ MCP           │               │
│  │ Service        │  │ Service       │               │
│  │                │  │               │               │
│  │ id: "knowledge"│  │ id: "mcp"     │               │
│  │ routes() → 15 │  │ routes() → 3  │               │
│  │ status() → {} │  │ status() → {} │               │
│  └───────────────┘  └───────────────┘               │
│                                                      │
│  merge_routes() → Router(18 routes)                  │
│  list_status()  → [{knowledge: {...}, mcp: {...}}]  │
└─────────────────────────────────────────────────────┘
```

**核心收益**：
- 每个服务自包含：路由定义、状态检查、启用/禁用逻辑都在服务内部
- 新增服务只需实现 Service trait + 注册到 ServiceRegistry
- router.rs 只需一行 `registry.merge_routes(state)` 即可获得所有服务路由
- Tauri 前端可通过 `get_service_statuses` 命令统一查看服务状态

## 三、Service trait 定义

### 3.1 trait 定义

**src-tauri/src/services/mod.rs**：

```rust
use async_trait::async_trait;
use axum::Router;
use serde::Serialize;
use std::sync::Arc;
use crate::AppState;
use crate::server::router::SharedState;

/// Service trait — all services implement this interface
#[async_trait]
pub trait Service: Send + Sync {
    /// Service unique id (e.g. "knowledge", "mcp")
    fn id(&self) -> &'static str;
    /// Display name (e.g. "知识库", "MCP Server")
    fn name(&self) -> &'static str;
    /// Description for UI display
    fn description(&self) -> &'static str;
    /// Whether enabled (default: true)
    fn enabled(&self) -> bool { true }
    /// Service status (async, may query DB)
    async fn status(&self, state: &Arc<AppState>) -> ServiceStatus;
    /// Register routes into a Router
    fn routes(&self, state: Arc<AppState>) -> Router<SharedState>;
}
```

**设计要点**：

1. **`async_trait`**：`status()` 是异步方法（需要查数据库），Rust trait 不原生支持 async fn，用 `async_trait` 宏桥接。
2. **`Send + Sync`**：Service 实例会被跨线程共享（Arc 包装），必须满足线程安全约束。
3. **`enabled()` 默认 true**：未来可扩展为从配置文件读取是否启用。
4. **`routes()` 接收 `Arc<AppState>`**：每个服务自己创建子路由器，AppState 提供 DB pool 等共享资源。

### 3.2 ServiceStatus 结构

```rust
#[derive(Debug, Serialize)]
pub struct ServiceStatus {
    pub id: String,
    pub name: String,
    pub description: String,
    pub enabled: bool,
    pub running: bool,
    pub stats: serde_json::Value,
}
```

**`stats` 用 `serde_json::Value`**：不同服务的统计数据结构不同（知识库统计 KB/文档/切片数量，MCP 统计可用工具数量），用 JSON Value 实现灵活性。

## 四、ServiceRegistry 实现

```rust
pub struct ServiceRegistry {
    services: Vec<Box<dyn Service>>,
}

impl ServiceRegistry {
    pub fn new() -> Self {
        let mut registry = Self { services: vec![] };
        // Register built-in services
        registry.register(Box::new(knowledge::KnowledgeService));
        registry.register(Box::new(mcp::McpService));
        registry
    }

    pub fn register(&mut self, service: Box<dyn Service>) {
        self.services.push(service);
    }

    /// Merge all service routes into one Router
    pub fn merge_routes(&self, state: Arc<AppState>) -> Router<SharedState> {
        let mut router = Router::new();
        for service in &self.services {
            if service.enabled() {
                router = router.merge(service.routes(state.clone()));
            }
        }
        router
    }

    /// Get all service statuses
    pub async fn list_status(&self, state: &Arc<AppState>) -> Vec<ServiceStatus> {
        let mut result = vec![];
        for service in &self.services {
            result.push(service.status(state).await);
        }
        result
    }
}
```

**关键设计**：

1. **`Vec<Box<dyn Service>>`**：动态分发，每个服务是不同的具体类型，但都实现 Service trait。
2. **`merge_routes`**：遍历所有已启用的服务，将它们的路由合并到一个大 Router。Axum 的 `Router::merge()` 会自动处理路由冲突（相同路径会 panic，所以各服务的路由前缀必须不同）。
3. **`list_status`**：异步遍历所有服务，收集状态信息。用于前端展示。

## 五、KnowledgeService 实现

**src-tauri/src/services/knowledge/mod.rs**：

```rust
pub struct KnowledgeService;

#[async_trait]
impl Service for KnowledgeService {
    fn id(&self) -> &'static str { "knowledge" }
    fn name(&self) -> &'static str { "知识库" }
    fn description(&self) -> &'static str {
        "本地知识库：创建私有知识库，上传文档自动向量化并构建 HNSW 索引，\
         通过 MCP 协议对外提供检索和 RAG 问答工具，支持任意 AI Agent 对接"
    }

    async fn status(&self, state: &Arc<AppState>) -> ServiceStatus {
        let pool = &state.db.pool;
        // Query real statistics from database
        let kb_count: i64 = sqlx::query_scalar("SELECT COUNT(*) FROM kb_knowledge_bases")
            .fetch_one(pool).await.unwrap_or(0);
        let doc_count: i64 = sqlx::query_scalar("SELECT COUNT(*) FROM kb_documents")
            .fetch_one(pool).await.unwrap_or(0);
        let chunk_count: i64 = sqlx::query_scalar("SELECT COUNT(*) FROM kb_chunks")
            .fetch_one(pool).await.unwrap_or(0);

        ServiceStatus {
            id: self.id().to_string(),
            name: self.name().to_string(),
            description: self.description().to_string(),
            enabled: true,
            running: true,
            stats: serde_json::json!({
                "knowledge_bases": kb_count,
                "documents": doc_count,
                "chunks": chunk_count,
            }),
        }
    }

    fn routes(&self, state: Arc<AppState>) -> Router<SharedState> {
        routes::create_router(state)
    }
}
```

## 七、Router 层集成

**src-tauri/src/server/router.rs**：

```rust
pub fn create_router(app: AppHandle, state: Arc<AppState>) -> Router {
    let shared = SharedState { app: app.clone(), state: state.clone() };
    let cors = CorsLayer::new()...;

    // Service registry — merge all service routes
    let registry = crate::services::ServiceRegistry::new();
    let service_router = registry.merge_routes(state.clone());

    Router::new()
        // Core API gateway routes (OpenAI / Anthropic / Responses)
        .route("/v1/chat/completions", post(handle_chat_completions))
        .route("/v1/completions", post(handle_completions))
        .route("/v1/responses", post(handle_responses))
        .route("/v1/embeddings", post(handle_embeddings))
        .route("/v1/models", get(handle_list_models))
        .route("/v1/messages", post(handle_messages))
        .route("/health", get(handle_health))
        // Service routes (Knowledge Base + MCP)
        .merge(service_router)
        .layer(cors)
        .with_state(shared)
}
```

**核心改动只有一行**：`.merge(service_router)` — 所有服务路由自动注册。

/// Get all service statuses (Knowledge Base, MCP, etc.)

## 九、services 模块组织

```
src-tauri/src/services/
├── mod.rs              # Service trait + ServiceRegistry + 模块注册
├── knowledge/          # 知识库服务
│   ├── mod.rs          # KnowledgeService 实现
│   ├── models.rs       # 数据模型
│   ├── repository.rs   # 数据库 CRUD
│   ├── parser.rs       # 文档解析
│   ├── splitter.rs     # 文本分块
│   ├── code_parser.rs  # tree-sitter 符号提取
│   ├── embedder.rs     # 向量化
│   ├── retriever.rs    # 检索（向量 + FTS5）
│   ├── rag.rs          # RAG 问答
│   ├── handlers.rs     # HTTP 处理函数
│   ├── routes.rs       # 路由注册
│   ├── importer.rs     # 多源导入
│   ├── index.rs        # HNSW 索引
│   └── processor.rs    # 文档处理流水线
├── mcp/                # MCP Server 服务
│   ├── mod.rs          # McpService 实现
│   └── handlers.rs     # MCP JSON-RPC 处理
```

**模块化原则**：
- 每个服务是一个独立子模块
- 子模块内部再按功能拆分（models/repository/handlers/routes 等）
- `mod.rs` 只做 Service trait 实现和子模块注册
- 对外暴露的接口只有 Service trait 实现和路由创建函数

## 十一、面试问题

1. **为什么 Service trait 用 `async_trait` 宏而不是直接写 `async fn`？Rust trait 对 async fn 的限制是什么？**

   > 提示：Rust trait 目前不支持 `async fn`（虽然 nightly 有实验性支持），因为 async fn 返回的未来类型是匿名的，无法在 trait 签名中命名。`async_trait` 宏将 async fn 转换为返回 `Pin<Box<dyn Future>>` 的普通 fn。

2. **ServiceRegistry 用 `Vec<Box<dyn Service>>` 存储服务实例，为什么不用 `HashMap<String, Box<dyn Service>>`？两种方式的取舍是什么？**

   > 提示：Vec 更简单、顺序注册即可；HashMap 可按 id 快速查找但增加复杂度。当前场景服务数量极少（2-3 个），Vec 遍历开销忽略不计。如果未来服务数量增多，HashMap 更合适。

3. **`merge_routes` 中 `service.enabled()` 检查的作用是什么？如果某个服务 disabled 但路由仍然存在会怎样？**

   > 提示：enabled 检查避免注册不需要的路由。如果 disabled 服务路由仍然存在，客户端请求会到达 handler 但可能返回 503 或空响应。在路由层过滤更干净——根本不会匹配到这些路由。

4. **`ServiceStatus.stats` 为什么用 `serde_json::Value` 而不是自定义枚举/结构体？这种"灵活类型"的代价是什么？**

   > 提示：不同服务的 stats 结构完全不同（知识库统计 KB/文档/切片，MCP 统计工具列表）。用 Value 避免为每个服务定义单独的 stats 类型。代价是失去类型安全，前端需要按 service.id 分支解析。

5. **`get_service_statuses` 每次调用都创建新的 `ServiceRegistry::new()`，这有什么性能影响？更好的做法是什么？**

   > 提示：ServiceRegistry::new() 只创建 Vec + 注册 2 个 Service struct，开销极小（微秒级）。但如果服务增多或 status() 变重（需要 DB 查询），可以考虑将 ServiceRegistry 存入 AppState 作为长期持有实例，避免重复创建。
