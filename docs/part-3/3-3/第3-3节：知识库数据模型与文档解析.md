## 二、数据库表结构设计

### 2.1 Migration 008 — 核心四表

知识库的核心是四张表，形成 **知识库 → 文档 → 切片** 的层级关系：

```
kb_knowledge_bases (知识库)
    │  1:N
kb_documents (文档)
    │  1:N
kb_chunks (切片 + 向量)
    
kb_tasks (处理任务)
```

**008_knowledge_base.sql**：

```sql
-- 知识库：一个知识库对应一个主题/项目
CREATE TABLE IF NOT EXISTS kb_knowledge_bases (
    id            TEXT PRIMARY KEY,
    name          TEXT NOT NULL,
    description   TEXT,
    status        INTEGER NOT NULL DEFAULT 1,      -- 1=active, 0=disabled
    doc_count     INTEGER NOT NULL DEFAULT 0,
    chunk_count   INTEGER NOT NULL DEFAULT 0,
    total_tokens  INTEGER NOT NULL DEFAULT 0,
    embedding_model  TEXT,                          -- 向量模型名
    embedding_channel_id TEXT,                      -- 向量渠道 ID
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);

-- 文档：上传的每个文件是一条记录
CREATE TABLE IF NOT EXISTS kb_documents (
    id            TEXT PRIMARY KEY,
    kb_id         TEXT NOT NULL,
    filename      TEXT NOT NULL,
    file_path     TEXT,                             -- 本地文件路径（如果是导入）
    file_type     TEXT NOT NULL,                    -- pdf/txt/md/docx/code...
    file_size     INTEGER NOT NULL DEFAULT 0,
    content_hash  TEXT NOT NULL,                    -- SHA256，防止重复上传
    chunk_count   INTEGER NOT NULL DEFAULT 0,
    token_count   INTEGER NOT NULL DEFAULT 0,
    status        TEXT NOT NULL DEFAULT 'pending',  -- pending/processing/ready/failed
    error_message TEXT,
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    FOREIGN KEY (kb_id) REFERENCES kb_knowledge_bases(id) ON DELETE CASCADE
);

-- 切片：文档被分块后的最小检索单元
CREATE TABLE IF NOT EXISTS kb_chunks (
    id             TEXT PRIMARY KEY,
    doc_id         TEXT NOT NULL,
    kb_id          TEXT NOT NULL,
    chunk_index    INTEGER NOT NULL,                -- 分块序号
    content        TEXT NOT NULL,                   -- 分块文本内容
    token_count    INTEGER NOT NULL DEFAULT 0,
    embedding      BLOB,                            -- 向量数据（二进制）
    embedding_dim  INTEGER NOT NULL DEFAULT 0,      -- 向量维度
    metadata       TEXT NOT NULL DEFAULT '{}',       -- JSON元数据
    created_at     TEXT NOT NULL,
    FOREIGN KEY (doc_id) REFERENCES kb_documents(id) ON DELETE CASCADE,
    FOREIGN KEY (kb_id) REFERENCES kb_knowledge_bases(id) ON DELETE CASCADE
);

-- 处理任务：记录异步处理进度
CREATE TABLE IF NOT EXISTS kb_tasks (
    id            TEXT PRIMARY KEY,
    kb_id         TEXT NOT NULL,
    doc_id        TEXT,
    task_type     TEXT NOT NULL,                    -- embed/index/import
    status        TEXT NOT NULL DEFAULT 'pending',
    progress      INTEGER NOT NULL DEFAULT 0,
    total_items   INTEGER NOT NULL DEFAULT 0,
    done_items    INTEGER NOT NULL DEFAULT 0,
    error_message TEXT,
    created_at    TEXT NOT NULL,
    completed_at  TEXT,
    FOREIGN KEY (kb_id) REFERENCES kb_knowledge_bases(id) ON DELETE CASCADE
);
```

**设计决策**：

| 决策点 | 选择 | 原因 |
|--------|------|------|
| 主键类型 | TEXT (UUID) | 避免自增ID暴露顺序信息，支持分布式场景 |
| embedding 存储 | BLOB | 向量是 f32 数组，用 bincode 序列化为二进制，比 JSON 存储节省 50% 空间 |
| 外键 | CASCADE | 删除知识库时自动删除关联文档和切片，避免孤儿数据 |
| content_hash | SHA256 | 防止重复上传同一文档，hash 相同则跳过 |
| status 字段 | pending→processing→ready→failed | 文档处理是异步的，需要状态追踪 |

### 2.4 Migration 011 — 符号感知

```sql
-- 为 chunk 新增符号信息（来自 tree-sitter AST 解析）
ALTER TABLE kb_chunks ADD COLUMN symbol_name TEXT;
ALTER TABLE kb_chunks ADD COLUMN symbol_kind TEXT;

-- 符号过滤索引（部分索引：只索引有 symbol_name 的行）
CREATE INDEX IF NOT EXISTS idx_chunks_symbol ON kb_chunks(kb_id, symbol_kind)
    WHERE symbol_name IS NOT NULL;
```

**symbol_name / symbol_kind**：代码文件不是按固定大小分块，而是按函数/类/方法边界分块。每个 chunk 对应一个代码符号，metadata 包含符号名和类型（function/class/method 等）。

**部分索引**（`WHERE symbol_name IS NOT NULL`）：非代码文件没有符号信息，部分索引只为代码 chunk 创建，节省空间和查询时间。

## 四、文档解析（parser.rs）

parser 模块负责将不同格式的文件提取为纯文本：

```
┌──────────────────────────────────────┐
│          Supported Formats            │
│  .txt / .md  → 直接读取文本           │
│  .pdf        → pdf_extract 提取文本    │
│  .docx/.doc  → docx_extract 提取文本  │
│  .pptx       → pptx_extract 提取文本  │
│  .xlsx/.csv  → 表格提取               │
│  .code       → 带语言标记的代码        │
│  .html       → 剥离标签提取正文        │
│  其他        → 尝试作为文本读取        │
└──────────────────────────────────────┘
```

**解析流程**：

```rust
pub fn parse_document(filename: &str, content: &[u8]) -> Result<ParsedDocument, String> {
    let ext = filename.rsplit('.').next().unwrap_or("").to_lowercase();
    let text = match ext {
        "txt" | "md" | "markdown" => String::from_utf8_lossy(content).to_string(),
        "pdf" => pdf_extract::extract_text(content)?,
        "docx" | "doc" => docx_extract::extract_text(content)?,
        "pptx" => pptx_extract::extract_text(content)?,
        "xlsx" | "csv" => extract_table_text(content, &ext)?,
        "html" | "htm" => extract_html_text(content)?,
        // 代码文件：标记语言类型，后续按符号分块
        ext if is_code_file(&ext) => String::from_utf8_lossy(content).to_string(),
        // 其他：尝试作为文本
        _ => String::from_utf8_lossy(content).to_string(),
    };

    Ok(ParsedDocument {
        text,
        file_type: determine_file_type(&ext),
        language: determine_language(&ext),
    })
}
```

## 五、文本分块（splitter.rs）

### 5.1 SplitConfig

```rust
pub struct SplitConfig {
    pub chunk_size: usize,      // 目标 token 数（默认 512）
    pub chunk_overlap: usize,   // 重叠 token 数（默认 64）
}
```

**chunk_size 和 chunk_overlap 的含义**：

- `chunk_size=512`：每个分块目标包含约 512 个 token
- `chunk_overlap=64`：相邻分块重叠约 64 个 token，确保检索时不会遗漏跨分块的语义

**Token 估算**：用简单启发式 `~4 chars per token`，避免引入重 tokenizer 依赖。

## 六、tree-sitter 符号感知（code_parser.rs）

### 6.1 为什么需要 tree-sitter？

代码文件如果按固定大小分块，一个函数会被切成两半，检索结果毫无意义。**tree-sitter 是增量解析器**，能提取 AST 中的符号边界（函数、类、方法），确保每个 chunk 是完整的代码符号。

### 6.2 Symbol 数据结构

```rust
pub struct Symbol {
    pub kind: SymbolKind,          // Function/Method/Class/Struct/...
    pub name: String,              // 符号名
    pub qualified_name: String,    // 限定名（Class.method）
    pub start_line: usize,         // 开始行（0-indexed）
    pub end_line: usize,           // 结束行（0-indexed, inclusive）
    pub signature: Option<String>, // 函数签名（第一行）
    pub docstring: Option<String>, // 文档注释（Python）
}

pub enum SymbolKind {
    Function, Method, Class, Struct, Interface,
    Enum, Variable, Constant, TypeAlias, Namespace,
}
```

### 6.3 支持的语言

```rust
fn get_language(ext: &str) -> Option<tree_sitter::Language> {
    match ext {
        "ts"  => Some(tree_sitter_typescript::LANGUAGE_TYPESCRIPT.into()),
        "tsx" => Some(tree_sitter_typescript::LANGUAGE_TSX.into()),
        "js" | "jsx" => Some(tree_sitter_javascript::LANGUAGE.into()),
        "py"  => Some(tree_sitter_python::LANGUAGE.into()),
        "rs"  => Some(tree_sitter_rust::LANGUAGE.into()),
        "go"  => Some(tree_sitter_go::LANGUAGE.into()),
        "java" => Some(tree_sitter_java::LANGUAGE.into()),
        _ => None,
    }
}
```

### 6.4 符号提取流程

```rust
pub fn extract_symbols(filename: &str, content: &str) -> Vec<Symbol> {
    // 1. 根据文件扩展名获取 tree-sitter Language
    // 2. 创建 Parser，设置语言
    // 3. 解析 content 为 AST (tree)
    // 4. 递归遍历 AST (walk_node)
    // 5. 对每种语言有专门的节点检查函数：
    //    - check_ts_js_node: function_declaration, class_declaration, method_definition...
    //    - check_python_node: function_definition, class_definition...
    //    - check_rust_node: function_item, struct_item, enum_item, trait_item...
    //    - check_go_node: function_declaration, type_declaration...
    //    - check_java_node: class_declaration, method_declaration...
    // 6. 返回符号列表
}
```

**递归遍历的关键逻辑**：

```rust
fn walk_node(node, source, ext, symbols, parent_name, parent_kind) {
    // 检查当前节点是否是目标符号
    let symbol_info = match ext {
        "ts" | "tsx" | "js" => check_ts_js_node(&kind, &node, source),
        "py" => check_python_node(&kind, &node, source, parent_kind),
        "rs" => check_rust_node(&kind, &node, source, parent_kind),
        ...
    };

    // 如果是符号，提取 name/qualified_name/start_line/end_line/signature
    if let Some((sym_kind, name, signature)) = symbol_info {
        symbols.push(Symbol { ... });
        // 更新 parent_name（嵌套符号需要限定名）
    }

    // 递归遍历子节点
    for child in node.children() {
        walk_node(child, source, ext, symbols, &next_parent, &next_kind);
    }
}
```

**Rust 特殊处理**：`function_item` 在 `implementation_item` 内部时是 Method，否则是 Function。通过 `parent_kind` 判断。

## 九、面试问题

1. **知识库的表结构为什么用 `kb_knowledge_bases → kb_documents → kb_chunks` 三层层级？两层（知识库 + 切片）是否足够？**

   > 提示：文档层提供了文件元信息（filename、file_type、file_size、content_hash）和状态追踪（pending→processing→ready→failed）。如果只有两层，这些信息要么丢失要么冗余存储在每个 chunk 中。三层结构还支持按文档管理（删除整个文档、重新索引单个文档）。

2. **`content_hash` 用 SHA256 的作用是什么？为什么不是 MD5？**

   > 提示：SHA256 防止重复上传同一文件（hash 相同则跳过）。SHA256 比 MD5 抗碰撞更强，虽然在这个场景下 MD5 也够用，但 SHA256 是更安全的选择。代价是计算稍慢，但文档上传不是高频操作。

3. **embedding 存储为 BLOB 而不是 JSON 字符串，为什么？具体节省多少空间？**

   > 提示：一个 1536 维的 f32 向量：BLOB = 1536×4 = 6144 bytes；JSON = `[0.123456, -0.789012, ...]` 约 1536×12 = 18432 bytes。BLOB 节省约 67% 空间。用 bincode 序列化更紧凑（无分隔符、无小数位冗余）。

4. **tree-sitter 的符号感知分块 vs 固定大小分块，各自的适用场景是什么？如果代码文件没有 tree-sitter 支持（比如 Haskell），会怎样？**

   > 提示：代码文件必须用符号感知分块，否则函数被截断。非代码文件（txt/md/pdf）用固定大小分块即可。不支持的语言会 fallback 到 split_text——效果不如符号分块但仍可用。`is_supported_language()` 检查决定走哪条路径。

5. **`chunk_overlap=64` 的重叠设计为什么重要？如果 overlap=0 会怎样？overlap 太大（比如 256）会有什么问题？**

   > 提示：overlap=0 时，跨分块的关键信息可能被截断（比如一个关键术语恰好出现在分块边界）。overlap 太大会增加冗余存储和检索噪声。64（约 chunk_size 的 12%）是经验值——足够保持语义连贯，又不至于过度冗余。
