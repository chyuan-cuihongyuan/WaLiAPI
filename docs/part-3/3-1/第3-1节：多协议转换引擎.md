## 二、为什么需要多协议转换？

### 2.1 现状问题

当前 WaLiAPI 只支持 OpenAI Chat Completions 格式。但实际场景中：

- **Anthropic Claude** 使用 `messages` 端点、`x-api-key` 认证、`content` 数组格式（含 text/tool_use/tool_result block）
- **OpenAI Responses API** 使用 `input` 替代 `messages`、`instructions` 替代 `system`、扁平化工具定义

下游应用（Cursor、Claude Desktop、MCP Client 等）往往直接使用供应商原生协议。如果每个应用都自己做格式适配，那是 N×M 的复杂度。

### 2.2 网关层统一转换

WaLiAPI 的选择是：**在网关层做协议转换，对外暴露三种端点，内部统一走 OpenAI 格式**。

```
┌─────────────────────────────────────────────────────┐
│              下游应用（三种协议）                      │
│  Cursor/OpenAI SDK ──→ /v1/chat/completions          │
│  Claude Desktop ────→ /v1/messages                  │
│  MCP Client ────────→ /v1/responses                  │
└───────────────────────┬─────────────────────────────┘
                        │ 三种请求格式
┌───────────────────────▼─────────────────────────────┐
│              WaLiAPI Protocol 层                      │
│  anthropic_to_openai() ──→ OpenAI 格式               │
│  responses_to_openai()  ──→ OpenAI 格式               │
│  Chat Completions 直接 → OpenAI 格式                  │
└───────────────────────┬─────────────────────────────┘
                        │ 统一 OpenAI 格式
┌───────────────────────▼─────────────────────────────┐
│              Proxy 层（渠道分发 + 重试）               │
│  dispatcher → adaptor → upstream                      │
└───────────────────────┬─────────────────────────────┘
                        │ OpenAI 格式响应
┌───────────────────────▼─────────────────────────────┐
│              Protocol 层反向转换                       │
│  openai_to_anthropic() ──→ Anthropic 格式            │
│  openai_to_responses()  ──→ Responses 格式            │
│  Chat Completions 直接 → OpenAI 格式                  │
└───────────────────────┬─────────────────────────────┘
                        │ 三种响应格式
┌───────────────────────▼─────────────────────────────┐
│              下游应用收到对应格式的响应                  │
└─────────────────────────────────────────────────────┘
```

**核心收益**：
- 下游应用零改动就能接入 WaLiAPI
- 内部 Proxy 只需处理一种格式（OpenAI），代码简洁
- 新增协议只需加转换层，不影响核心 Proxy 逻辑

### 3.2 mod.rs — 通用工具

**src-tauri/src/protocol/mod.rs**：

```rust
pub mod responses;
pub mod anthropic;

/// Extract API key from either `Authorization: Bearer xxx` or `x-api-key: xxx` header.
pub fn extract_api_key(headers: &axum::http::HeaderMap) -> Option<String> {
    // Try Authorization: Bearer xxx first
    if let Some(auth) = headers.get("authorization").and_then(|h| h.to_str().ok()) {
        if let Some(key) = auth.strip_prefix("Bearer ") {
            let trimmed = key.trim();
            if !trimmed.is_empty() {
                return Some(trimmed.to_string());
            }
        }
    }
    // Fall back to x-api-key
    if let Some(key) = headers.get("x-api-key").and_then(|h| h.to_str().ok()) {
        let trimmed = key.trim();
        if !trimmed.is_empty() {
            return Some(trimmed.to_string());
        }
    }
    None
}

/// Detect if a request is in Anthropic format by checking headers.
pub fn is_anthropic_request(headers: &axum::http::HeaderMap, body: &serde_json::Value) -> bool {
    if headers.contains_key("anthropic-version") { return true; }
    if headers.contains_key("x-api-key") && !headers.contains_key("authorization") { return true; }
    let _ = body;
    false
}

/// Detect if a request targets the Responses API format.
pub fn is_responses_request(body: &serde_json::Value) -> bool {
    body.get("input").is_some() && body.get("messages").is_none()
}
```

**设计要点**：

1. **extract_api_key**：Anthropic 用 `x-api-key`，OpenAI 用 `Authorization: Bearer`。统一提取逻辑，优先 Bearer，次选 x-api-key。
2. **is_anthropic_request**：基于 header 检测，比 body 检测更可靠（`anthropic-version` header 是 Anthropic SDK 标配）。
3. **is_responses_request**：Responses API 用 `input` 替代 `messages`，这是最可靠的区分信号。

## 四、Anthropic 协议转换

### 4.1 Anthropic 请求 → OpenAI 格式

Anthropic Messages API 请求格式与 OpenAI Chat Completions 有多处差异：

| 特征 | Anthropic | OpenAI |
|------|-----------|--------|
| 系统消息 | `system` 字段（顶层） | `messages[0].role="system"` |
| 内容格式 | `content` 数组（text/tool_use/tool_result block） | `content` 字符串 |
| 工具定义 | `input_schema` + `type: "custom"` | `function.parameters` + 嵌套结构 |
| 工具选择 | `type: "auto"/"any"/"tool"` | `"auto"/"required"/{function:{name}}` |
| 认证 | `x-api-key` header | `Authorization: Bearer` |
| 停止序列 | `stop_sequences` | `stop` |

**转换核心逻辑**：

```rust
pub fn anthropic_to_openai(body: &Value) -> Value {
    let model = body.get("model").and_then(|m| m.as_str()).unwrap_or("").to_string();
    let messages = body.get("messages").cloned().unwrap_or(Value::Array(vec![]));
    let max_tokens = body.get("max_tokens").and_then(|m| m.as_u64()).unwrap_or(4096);
    let stream = body.get("stream").and_then(|s| s.as_bool()).unwrap_or(false);

    // Extract system message and prepend it
    let system = body.get("system").and_then(|s| {
        if let Some(str_val) = s.as_str() {
            Some(str_val.to_string())
        } else if let Some(arr) = s.as_array() {
            let texts: Vec<String> = arr.iter().filter_map(|block| {
                block.get("text").and_then(|t| t.as_str()).map(|s| s.to_string())
            }).collect();
            Some(texts.join(""))
        } else { None }
    });

    // Convert Anthropic message content (array format) to OpenAI string format
    let openai_messages = convert_anthropic_messages_to_openai(&messages, system);

    let mut openai_body = serde_json::json!({
        "model": model,
        "messages": openai_messages,
        "max_tokens": max_tokens,
        "stream": stream,
    });
    // ... temperature, top_p, stop_sequences, tools, tool_choice 转换
    openai_body
}
```

### 4.2 Anthropic 内容数组 → OpenAI 字符串

Anthropic 的 `content` 字段是数组，每项有 `type`（text/tool_use/tool_result/thinking/image）。需要逐块解析：

```rust
fn convert_anthropic_messages_to_openai(messages: &Value, system: Option<String>) -> Value {
    let mut msgs = Vec::new();
    // Prepend system message if present
    if let Some(sys) = system {
        msgs.push(serde_json::json!({"role": "system", "content": sys}));
    }

    if let Some(arr) = messages.as_array() {
        for msg in arr {
            let role = msg.get("role").and_then(|r| r.as_str()).unwrap_or("user").to_string();
            if let Some(content_arr) = msg.get("content").and_then(|c| c.as_array()) {
                let mut text_parts: Vec<String> = Vec::new();
                let mut tool_calls: Vec<Value> = Vec::new();
                let mut tool_results: Vec<Value> = Vec::new();

                for block in content_arr {
                    match block.get("type").and_then(|t| t.as_str()).unwrap_or("") {
                        "text" => { /* 收集文本 */ }
                        "tool_use" => {
                            // Anthropic tool_use → OpenAI assistant tool_calls
                            tool_calls.push(serde_json::json!({
                                "id": block.get("id")...,
                                "type": "function",
                                "function": { "name": ..., "arguments": ... }
                            }));
                        }
                        "tool_result" => {
                            // Anthropic tool_result → OpenAI tool message
                            tool_results.push(serde_json::json!({
                                "role": "tool",
                                "tool_call_id": block.get("tool_use_id")...,
                                "content": result_content
                            }));
                        }
                        "thinking" => { /* 提取推理文本 */ }
                        "image" => { /* 跳过，未来转换 */ }
                        _ => {}
                    }
                }
                // 根据 tool_calls/tool_results/text 的组合决定最终消息格式
            }
        }
    }
    Value::Array(msgs)
}
```

**关键转换规则**：
- `tool_use` → `assistant.tool_calls[].function`（Anthropic 的 `input` 是 JSON 对象，OpenAI 的 `arguments` 是 JSON 字符串）
- `tool_result` → `tool` role message（`tool_use_id` → `tool_call_id`）
- `thinking` → 纯文本追加（OpenAI 没有原生 thinking block）
- 系统消息从顶层 `system` 字段提取，插入 `messages[0]`

### 4.3 OpenAI 响应 → Anthropic 格式

反向转换处理 `choices[0].message` → Anthropic 的 `content` 数组：

```rust
pub fn openai_to_anthropic(openai_resp: &Value, model: &str) -> Value {
    // ...提取 message, content_text, finish_reason

    // finish_reason 映射
    let stop_reason = match finish_reason {
        "stop" => "end_turn",
        "length" => "max_tokens",
        "tool_calls" => "tool_use",
        _ => "end_turn",
    };

    // 构建 content 数组
    let mut content_blocks = Vec::new();
    if !content_text.is_empty() {
        content_blocks.push(serde_json::json!({"type": "text", "text": content_text}));
    }
    // tool_calls → tool_use blocks
    if let Some(tool_calls) = message.and_then(|m| m.get("tool_calls")).and_then(|t| t.as_array()) {
        for tc in tool_calls {
            content_blocks.push(serde_json::json!({
                "type": "tool_use",
                "id": tc.get("id")...,
                "name": tc.get("function").get("name")...,
                "input": serde_json::from_str(arguments_str)... // JSON 字符串 → JSON 对象
            }));
        }
    }

    serde_json::json!({
        "id": ...,
        "type": "message",
        "role": "assistant",
        "model": model,
        "content": content_blocks,
        "stop_reason": stop_reason,
        "usage": { "input_tokens": ..., "output_tokens": ... }
    })
}
```

### 4.4 Anthropic SSE 流式转换

这是最复杂的部分。Anthropic 的 SSE 事件序列与 OpenAI 完全不同：

**OpenAI SSE 流式序列**：
```
data: {"choices":[{"delta":{"role":"assistant"}}]}
data: {"choices":[{"delta":{"content":"Hello"}}]}
data: {"choices":[{"delta":{"content":" world"}}]}
data: {"choices":[{"delta":{},"finish_reason":"stop"}]}
data: [DONE]
```

**Anthropic SSE 流式序列**：
```
event: message_start    → 整体消息开始
event: content_block_start → 文本/工具块开始
event: content_block_delta → 文本增量 / input_json_delta
event: content_block_stop  → 块结束
event: message_delta      → stop_reason + usage
event: message_stop       → 整体结束
```

转换需要维护状态（`AnthropicStreamState`）：

```rust
pub struct AnthropicStreamState {
    pub started: bool,           // 是否已发送 message_start
    pub input_tokens: u64,
    pub output_tokens: u64,
    text_block_open: bool,       // 文本块是否已开启
    text_block_stopped: bool,    // 文本块是否已关闭
    tool_calls: HashMap<usize, ToolCallState>,  // 工具调用状态追踪
    next_block_index: usize,     // 下一个 content block 编号
    thinking_block_open: bool,   // 推理块状态
    thinking_block_index: usize,
}
```

**转换流程图**：

```
OpenAI delta.content="Hello"
  → Anthropic: content_block_start(index=0, type=text)  [首次]
  → Anthropic: content_block_delta(index=0, text_delta="Hello")

OpenAI delta.tool_calls[0].id="call_123", name="search"
  → Anthropic: content_block_stop(index=0)  [关闭文本块]
  → Anthropic: content_block_start(index=1, type=tool_use, id="call_123", name="search")

OpenAI delta.tool_calls[0].function.arguments='{"qu'
  → Anthropic: content_block_delta(index=1, input_json_delta='{"qu')

OpenAI finish_reason="stop"
  → Anthropic: content_block_stop(所有未关闭的块)
  → Anthropic: message_delta(stop_reason="end_turn")
  → Anthropic: message_stop
```

## 五、Responses API 协议转换

### 5.1 Responses API 的设计动机

OpenAI 在 2025 年推出了 Responses API，相比 Chat Completions API：

| 特征 | Chat Completions | Responses |
|------|-----------------|-----------|
| 输入字段 | `messages` 数组 | `input` 数组（更灵活） |
| 系统指令 | `system` role message | `instructions` 顶层字段 |
| 工具定义 | 嵌套 `function` | 扁平 `name/parameters` |
| 输出格式 | `choices[].message` | `output[]` 数组 |
| 工具调用输出 | `tool_calls` + `tool role` | `function_call` + `function_call_output` |
| 内置工具 | 无 | `web_search/file_search/computer_use` |

Responses API 更适合 AI Agent 场景——它的 `input/output` 是扁平数组，更方便 Agent 拼接对话上下文。

### 5.2 Responses 请求 → OpenAI 格式

```rust
pub fn responses_to_openai(body: &Value) -> Value {
    let model = body.get("model").and_then(|m| m.as_str()).unwrap_or("").to_string();

    // Convert input array to messages array
    let messages = if let Some(input) = body.get("input") {
        convert_responses_input_to_messages(input)
    } else {
        Value::Array(vec![])
    };

    // max_output_tokens → max_tokens
    let max_tokens = body.get("max_output_tokens").and_then(|m| m.as_u64()).unwrap_or(4096);
    let stream = body.get("stream").and_then(|s| s.as_bool()).unwrap_or(false);

    let mut openai_body = serde_json::json!({
        "model": model,
        "messages": messages,
        "max_tokens": max_tokens,
        "stream": stream,
    });
    // ... temperature, top_p, tools, tool_choice, instructions 转换
    openai_body
}
```

**input 数组转换规则**：

- `type: "message"` → 标准消息（提取 `content` 数组中的 `text`）
- `type: "function_call"` → `assistant.tool_calls[]`
- `type: "function_call_output"` → `tool` role message
- `instructions` 字段 → `system` role message 插入 `messages[0]`

### 5.3 Responses 工具格式转换

Responses API 工具是扁平的：

```json
// Responses API 扁平格式
{"type": "function", "name": "search", "parameters": {...}, "description": "..."}
```

需要转换成 OpenAI 嵌套格式：

```json
// OpenAI 嵌套格式
{"type": "function", "function": {"name": "search", "parameters": {...}, "description": "..."}}
```

内置工具（`web_search/file_search/computer_use`）被跳过——它们只在 OpenAI 原生 API 有意义，通过网关转发到其他供应商没有意义。

### 5.4 OpenAI 响应 → Responses 格式

```rust
pub fn openai_to_responses(openai_resp: &Value, model: &str) -> Value {
    // ...提取 choice, message, content, finish_reason

    // 构建 output 数组
    let mut output = Vec::new();

    // tool_calls → function_call 输出项
    if let Some(tool_calls) = message.and_then(|m| m.get("tool_calls")).and_then(|t| t.as_array()) {
        for tc in tool_calls {
            output.push(serde_json::json!({
                "id": format!("fc_{}", uuid::Uuid::new_v4().simple()),
                "type": "function_call",
                "call_id": tc.get("id")...,
                "name": ...,
                "arguments": ...,
                "status": "completed"
            }));
        }
    }

    // 文本内容 → message 输出项
    if !content.is_empty() || output.is_empty() {
        output.push(serde_json::json!({
            "id": format!("msg_{}", uuid::Uuid::new_v4().simple()),
            "type": "message",
            "role": "assistant",
            "content": [{"type": "output_text", "text": content}],
            "status": "completed"
        }));
    }

    serde_json::json!({
        "id": ...,
        "object": "response",
        "created_at": ...,
        "model": model,
        "output": output,
        "usage": {...},
        "status": "completed",
        "finish_reason": finish_reason
    })
}
```

## 六、Handlers 层路由处理

### 6.1 Anthropic Messages 路由

**src-tauri/src/server/handlers.rs**：

```rust
pub async fn handle_messages(
    State(shared): State<SharedState>,
    headers: HeaderMap,
    body: axum::body::Bytes,
) -> Response {
    let json: serde_json::Value = match serde_json::from_str(&body_str) {
        Ok(j) => j,
        Err(e) => return (StatusCode::BAD_REQUEST, format!("Invalid JSON: {}", e)).into_response(),
    };

    // Anthropic 用 x-api-key 或 Authorization Bearer
    let api_key = match protocol::extract_api_key(&headers) {
        Some(k) => k,
        None => return (StatusCode::UNAUTHORIZED, Json(serde_json::json!({
            "type": "error",
            "error": {"type": "authentication_error", "message": "Missing API key"}
        }))).into_response(),
    };

    // 转换 Anthropic 请求为 OpenAI 格式
    let openai_body = protocol::anthropic_to_openai(&json);

    if is_stream {
        handle_messages_stream(shared, openai_body, model, ...).await
    } else {
        // 转换 OpenAI 响应回 Anthropic 格式
        let anthropic_resp = protocol::openai_to_anthropic(&result.body, &model);
        (StatusCode::OK, Json(anthropic_resp)).into_response()
    }
}
```

**错误响应格式差异**：
- OpenAI: `{"error": {"message": "...", "type": "...", "code": ...}}`
- Anthropic: `{"type": "error", "error": {"type": "...", "message": "..."}}`

## 十、面试问题

1. **为什么 WaLiAPI 选择在网关层做协议转换，而不是让下游应用各自适配不同供应商的 API 格式？**

   > 提示：考虑 N×M 的适配矩阵复杂度、维护成本、以及网关层统一转换后新增协议只需加转换层的扩展性优势。

2. **Anthropic 的 SSE 流式事件与 OpenAI 的 SSE 流式事件在结构上有哪些关键差异？转换时最容易踩的坑是什么？**

   > 提示：OpenAI 是 `delta.content` 逐字推送，Anthropic 需要 `message_start → content_block_start → content_block_delta → content_block_stop → message_delta → message_stop` 完整生命周期。踩坑点：状态追踪（文本块何时关闭、tool_use 块的 index 管理）。

3. **Responses API 和 Chat Completions API 的核心区别是什么？为什么 OpenAI 要推出 Responses API？**

   > 提示：Chat Completions 是对话式（messages 数组），Responses 是 Agent 式（input/output 扁平数组 + 内置工具）。Responses API 更适合 MCP 和 Agent 场景。

4. **tool_use 和 tool_calls 的转换中，`input`（JSON 对象）和 `arguments`（JSON 字符串）的互转有什么需要注意的边界情况？**

   > 提示：`serde_json::to_string` 可能因特殊字符失败；`serde_json::from_str` 对不完整 JSON 会报错（流式场景下 arguments 是增量拼接的）。

5. **`extract_api_key` 为什么优先检查 `Authorization: Bearer` 而不是 `x-api-key`？这种优先级选择有什么实际场景依据？**

   > 提示：有些应用（如 Cursor）发送 Anthropic 请求时也带 Bearer header。优先 Bearer 可以兼容这种"混合认证"场景，避免错误提取到空 key。
